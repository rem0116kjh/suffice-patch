# SufficePatch

Intent → context → minimal solution → plan → implement → verify → STOP.
Optimize total work subject to correctness, safety, and the user's full request.

## Decide

Define the requested behavior and evidence that would prove completion. Preserve
applicable project instructions and unrelated changes. YAGNI removes speculative
work, never explicit requirements.

Start at the lowest sufficient context level:
- **L0:** prompt only.
- **L1:** 1–3 directly relevant files.
- **L2:** related module, callers, helpers, tests.
- **L3:** cross-module contracts, configuration, architecture.
- **L4:** repository-wide investigation.

Read known files directly; otherwise search paths/symbols with bounded output.
Batch independent reads or checks in one tool call. Do not reread evidence already
available. Escalate for a concrete missing fact; briefly name it. Safety and shared
contracts can require jumping levels; file counts are guides, not caps. Stop
research when the change location, contract, reuse options, and verification path
are known with no material correctness/security uncertainty. External primary
docs are for unresolved API/version questions, not a mandatory registry search.

Choose the first adequate solution: needed at all? → existing code → stdlib →
native platform → installed dependency → tiny local edit → minimum implementation.

Budget change risk: existing code reuse → existing dependency → stdlib/native →
local edit → small helper → new abstraction → new dependency → architecture change.
Existing project usage usually wins; stdlib/native beats an equivalent unused
dependency API. These are decision guides, not mandatory tool calls. Lower rungs
need stronger evidence that cheaper choices cannot satisfy the contract.
Before adding any helper, wrapper, abstraction, configuration layer, dependency,
refactor, speculative feature, or architecture change, ask: necessary for this
request? If no, omit it. One CSS rule need not become a component.

## Do and prove

Pick the smallest change and a check that could falsify it. Keep trivial plans
mental and multi-step plans short; do not create planning documents by default.
Reproduce bugs/add regression tests first when needed to establish correctness;
use existing test infrastructure. Fix causes at the appropriate shared boundary
and check affected callers, not just the reported symptom. Do not code-golf.

Never minimize authentication, authorization, trust-boundary input validation,
security validation, data-loss prevention, transaction/data integrity,
accessibility, required error handling, or tests needed to prove correctness.

Review the diff for scope, contracts, edge cases, and these safety invariants.
Choose the cheapest sufficient verification: syntax/type → targeted test → module
→ integration → full suite. Skip inapplicable rungs; syntax does not prove
behavior. Shared/security-sensitive changes or uncertain impact need broader
checks. Preserve required project checks; use browser/keyboard or rollback checks
when relevant. Failures guide fixes and affected rechecks. Do not repeat passed
checks without new changes, unresolved risk, or a requirement. Missing/unrun
checks are unverified; never weaken tests to get green.

## Stop

STOP when the request is implemented, sufficient checks pass, review finds no
unresolved material issue introduced by the change, and only necessary changes
remain. Report outcome, actual verification, and limitations. Then stop: no
optional refactor, abstraction, documentation, dependency, architecture work,
or extra review cycle. Requested documentation remains in scope.

If blocked, report the missing prerequisite/evidence; budget exhaustion is not
success. Continue authorized independent work when possible. Remember lessons
only on explicit request through an existing memory mechanism, without secrets.
Improve this skill only in a separate requested eval. No automatic memory,
self-rewriting, persistent modes, hooks, or additional skill loading.
